# 向量库内容分析：什么需要入库，什么不需要

## 背景

当前 SRM_agent 的 Chroma 向量库只有一份静态知识文件 `supplier_guide.txt`（供应商管理 SOP 手册），Agent 已有两个工具通过实时 API 查询 MySQL 数据（`search_suppliers`、`get_price_reference`）。需要判断还有哪些数据适合加入向量库。

---

## 核心判断原则

| 适合向量库 | 不适合向量库 |
|---|---|
| 非结构化/自由文本，需要语义搜索 | 结构化枚举值，SQL WHERE 精确匹配即可 |
| 相对静态、不频繁变动的数据 | 实时变动数据（订单状态、库存） |
| 用户会以自然语言模糊查询的内容 | 数值范围/日期范围查询 |
| 跨字段综合语义匹配 | 敏感数据（密码、手机号） |

---

## 分层分析

### 第一层：已经在向量库 — 保留

**`supplier_guide.txt`（供应商管理SOP手册）**

- 内容：资质等级标准、评估方法（5维度评分）、询比价流程（7步）、状态流转规则、成本管理（阶梯折扣）、风险管控（5类风险+应对策略）
- **理由**：纯非结构化文档，用户问"怎么评估供应商"时依赖语义匹配，无结构化表可查
- **结论**：不动

### 第二层：建议加入向量库 — 高价值

#### 1. 供应商档案文本（每条供应商生成一个文本摘要）

来源：`srm_supplier` 表

聚合字段构成描述文本：
```
"{supplierName}，位于{region}，主营{mainCategory}，
 资质等级{qualificationLevel}级，地址{address}。备注：{remark}"
```

示例：
```
"深圳华强电子有限公司，位于华南，主营电子元器件，
 资质等级3级，地址深圳市南山区科技园。备注：专注军工级芯片代理，交期稳定"
```

**理由**：
- 用户查询 "推荐做电子元器件的华东供应商" 时需要语义匹配
- `mainCategory` 的"电子元器件" vs 用户说的"芯片" vs "半导体" —— SQL LIKE 做不到语义泛化
- `remark` 字段是自由文本，含有关键的业务信息（如"专注军工级"），只有向量搜索能有效检索
- 供应商档案数据相对稳定，不需要频繁重建索引

#### 2. 历史成交案例摘要（订单 + 供应商 JOIN 生成文本）

每条订单生成：
```
"从{supplierName}采购{materialName}，数量{quantity}个，
 单价{unitPrice}元，总价{totalAmount}元，交货日期{deliveryDate}"
```

**理由**：
- 用户问"上次不锈钢板找谁买的？多少钱？"——需要跨物料名语义匹配
- "不锈钢板" vs "304不锈钢" vs "冷轧板" —— 需要语义泛化
- 为 Agent 的"询比价"决策提供历史上下文，这是 readme 中 RAG 优先级 4 的核心场景

### 第三层：暂不建议加入向量库

#### 3. 字典项（dict_item）

- 已有 `REGION_MAP` 和 `CATEGORY_KEYWORDS` 在 `agent_tools.py` 中做关键词映射
- 字典数据量小（几十条），枚举映射比向量搜索更快更准
- **结论**：不需要，当前方案已足够

#### 4. 用户表

- `department` 有一定语义价值，但采购场景中极少按用户搜索
- 敏感字段多（密码、手机号），不应入库
- **结论**：不需要

#### 5. 订单实时状态

- 订单状态频繁变更，重建索引成本高
- `get_price_reference` 工具已经通过 API 实时查询
- **结论**：不需要，实时 API 查询即可

### 第四层：绝对不要放入向量库

- `status`、`qualificationLevel` 等枚举字段 → SQL WHERE 精确过滤（硬过滤层）
- `unitPrice`、`totalAmount` 等数值 → 数值范围查询不适合向量
- `deliveryDate` 等日期 → 时间范围比较不适合向量
- `password`、`phone` → 敏感数据

---

## 建议入库优先级

```
优先级1（已有）：supplier_guide.txt 静态知识        ← 不动
优先级2（建议）：供应商档案文本                      ← 每条供应商一个 chunk
优先级3（建议）：历史成交案例摘要                    ← 每条订单一个 chunk
暂不入库：    字典、用户、实时订单状态、枚举/数值字段
```

---

## 数据流设计（后续实施参考）

```
Java 后端（MySQL）
    │
    │  定时/触发同步
    ▼
Python Agent（Chroma）
    │
    │  语义检索 (k=3)
    ▼
Agent Tool: search_supplier_knowledge
```

同步策略：供应商档案按 MD5 去重增量同步（复用现有 `VectorStoreService.load_document()` 机制），历史成交案例同理。

---

## 验证方式

1. 启动 Java 后端 → 确认 `/api/supplier` 和 `/api/order` 返回真实数据
2. 启动 Python Agent → 确认 Chroma 向量库加载成功
3. 发送测试 query 如 "推荐华南地区做电子元器件的供应商" → 确认 Agent 返回的供应商来自真实数据库而非硬编码
